HEALTHCARE ANALYTICS LAB - PART 3.1: STAR SCHEMA DESIGN DECISIONS

This document explains the choices I made when designing the star schema
(healthcare_analysis_data_warehouse, in star_schema.sql). I built it in
PostgreSQL 18.6 next to the original normalized schema (healthcare_oltp).

The lab's sample data only has four encounters, which is far too small to see
any performance difference, so I kept those rows and generated test data on
top of them with database_setup/03_generate_test_data.sql. That gave me about
1 million encounters, 2.5 million diagnosis rows, 2 million procedure rows and
900,000 billing rows. All the numbers in this document come from that data.


DECISION 1: FACT TABLE GRAIN

I chose Option A: one row per encounter (fact_encounters).

The main reason is that three of the four questions are really about
encounters:

- Q1 counts encounters and unique patients per month, specialty and visit
  type. With one row per encounter, COUNT(*) simply is the number of
  encounters. If the fact were one row per diagnosis or per procedure, each
  encounter would appear 2-2.5 times on average, and I would need
  COUNT(DISTINCT encounter) everywhere just to undo that.

- Q3 is about readmissions, and an inpatient stay is an encounter. Whether a
  stay was followed by a readmission is a property of that encounter, so I
  can calculate it once in the ETL and store it on the row.

- Q4 is about revenue, and billing belongs to the encounter. With one row per
  encounter the allowed amount appears exactly once, so SUM() is correct. At
  diagnosis level the same money would be repeated on every diagnosis row
  and revenue would be counted two or three times, unless I split the amount
  across diagnoses, which gets complicated fast.

Q2 (diagnosis-procedure pairs) is the only question that needs more detail
than one row per encounter. Instead of changing the whole model for that one
question, I handle it with bridge tables connected to the encounter fact
(see Decision 4).

An encounter is also what both doctors and finance people think of as "one
visit", which makes the model easy to explain, and it keeps the fact table
at 1 million rows instead of 2-2.5 million.

Why I didn't choose the other options:
- Option B (one row per diagnosis) would make the table 2.5 times bigger,
  make revenue and encounter counts wrong unless every query used DISTINCT,
  and repeat the readmission flag on every diagnosis row.
- Option C (one row per procedure) has the same problems, plus encounters
  without any procedure would disappear completely. In my data that's
  199,899 encounters, about 20%, so I would need fake rows to keep them.


DECISION 2: DIMENSION TABLES

Every dimension has its own surrogate key (for example patient_key), which
PostgreSQL generates automatically (GENERATED BY DEFAULT AS IDENTITY). I also
keep the original ID from the source system (patient_id and so on), so I can
always trace a row back to where it came from and match it during the ETL.

Every dimension also has an "Unknown" row with key -1. If the ETL can't find
a match for something, the encounter points to -1 instead of being dropped,
and the foreign keys on the fact table are never empty.

dim_date
One row per day from 2015 to 2035. The columns are date_key, calendar_date,
year, quarter, quarter_label (like '2024-Q2'), month, month_name, year_month
(like '2024-05'), month_start_date, week_of_year, day_of_month, day_of_week,
day_name, is_weekend, fiscal_year and fiscal_quarter.
- The fact table uses this dimension three times: for the visit date, the
  discharge date and the first claim date.
- The key is the date as a number, like 20240510. It's easy to read, and
  dividing by 100 gives the month (202405), so queries can group by month
  with simple integer maths instead of formatting dates.
- I assumed a fiscal year that starts on 1 October.

dim_patient (SCD Type 1)
patient_key, patient_id, mrn, first_name, last_name, full_name, gender,
date_of_birth, age_group ('0-17', '18-39', '40-64', '65-79', '80+'),
row_hash and updated_at.
- I used Type 1 (overwrite) because changes to patient details are usually
  corrections. It also means each patient has exactly one patient_key, so
  COUNT(DISTINCT patient_key) gives a true count of unique patients.
- age_group here is the patient's current age band. The age at the time of
  each visit is stored on the fact table instead, because that value should
  never change afterwards.
- row_hash is an md5 of the main fields, which the ETL uses to see quickly
  whether a patient actually changed.

dim_provider (SCD Type 2)
provider_key, provider_id, first_name, last_name, full_name, credential,
specialty_key, specialty_name, department_key, department_name, row_hash,
effective_from, effective_to and is_current.
- I used Type 2 here because if a doctor changes specialty, their old visits
  should stay with their old specialty. Last year's cardiology visits should
  still show up as cardiology.
- Each row is one version of the provider, valid between effective_from and
  effective_to. A partial unique index on provider_id (only where is_current
  is true) makes sure a provider can never have two current versions.
- I copied the specialty and department names into this table so you can
  look at a provider's details without joining more tables.

dim_specialty (SCD Type 1)
specialty_key, specialty_id, specialty_name, specialty_code.

dim_department (SCD Type 1)
department_key, department_id, department_name, floor, capacity.

dim_encounter_type
encounter_type_key, encounter_type_name ('Outpatient', 'Inpatient', 'ER'),
care_setting ('Ambulatory', 'Acute', 'Emergency') and is_inpatient. It only
has four rows (the three types plus Unknown). Instead of repeating a text
value like 'Outpatient' on a million rows, the fact table stores a small
number, and the dimension adds useful groupings.

dim_diagnosis
diagnosis_key, diagnosis_id, icd10_code, icd10_description and
icd10_chapter (the first letter of the code, useful for grouping diagnoses).
It's used through the diagnosis bridge, and also directly from the fact
table for the primary diagnosis.

dim_procedure
procedure_key, procedure_id, cpt_code, cpt_description. Used through the
procedure bridge.

Why specialty appears both on the fact and on the provider
I put specialty_key directly on the fact table, which is the most important
change compared to the OLTP schema. In the OLTP schema you have to go from
encounters to providers to specialties to find a visit's specialty. In my
star schema, Q1, Q3 and Q4 only need one join to a 12-row table. The value
is taken from the provider version that was valid on the visit date, so it
stays historically correct. The specialty name on dim_provider is just there
for convenience when looking at providers.


DECISION 3: PRE-AGGREGATED METRICS

These are the values I calculate once in the ETL and store on each fact row:

- diagnosis_count: the number of different diagnoses on the visit. Without
  it, I'd have to join and group the 2.5 million row diagnosis table.
- procedure_count: the number of procedures (repeats included). Same idea
  for the 2 million procedure rows.
- primary_diagnosis_key: the diagnosis with sequence 1, so reports about
  the main reason for a visit don't need the bridge table at all.
- claim_count, total_claim_amount and total_allowed_amount: the billing
  totals per visit. This is what lets Q4 work without touching the billing
  table (900,000 rows) at all.
- claim_date_key: the date of the first claim, so revenue can be grouped by
  billing month. Visits that were never billed get -1.
- length_of_stay_hours and length_of_stay_days, so nobody has to do date
  arithmetic in their queries.
- patient_age_at_encounter, so age analysis doesn't need the patient table.
- is_index_inpatient_stay: true for completed inpatient stays.
- is_readmitted_30d: true if the same patient had another inpatient
  admission within 30 days of being discharged. This replaces the expensive
  self-join that the OLTP version of Q3 needs.
- days_to_next_admission: the number of days until that next admission.
  Keeping the actual number means a 7, 60 or 90-day version of the question
  can be answered without redoing the self-join.

For readmissions I used the same rule everywhere (the OLTP query, the ETL and
the star query): a stay counts if it's an inpatient visit with a discharge
date, and it's readmitted if the same patient comes back as an inpatient
within 30 days. On my data that's 8,901 out of 150,393 stays (5.92%), and
both versions give exactly the same number.

Why this helps performance:
- Each of these columns replaces a join with a large table (or a self-join on
  1 million rows) with a value that's already sitting on the row.
- The work happens once per ETL run instead of every time someone opens a
  report.
- Counts and amounts can be added up safely at any level (per month, per
  specialty, per department), so everything can be answered from the fact
  table alone.
- Definitions like "readmission" are calculated in one place, so every
  report uses the same rule.

The one thing I couldn't pre-calculate is the number of unique patients.
Distinct counts don't add up: the unique patients for a year aren't the sum
of the unique patients per month, because the same person can visit in
several months. So Q1 still has to count them when it runs.


DECISION 4: BRIDGE TABLES

Yes, I used bridge tables: bridge_encounter_diagnoses and
bridge_encounter_procedures. I also added a summary table, agg_dx_px_pair,
for Q2.

The relationship between encounters and diagnoses (and between encounters and
procedures) is truly many-to-many. One visit can have several diagnoses, and
one diagnosis appears on many visits. To put this directly into the fact
table, I would have to either change the grain (which I rejected in Decision
1), add fixed columns like dx1 to dx10 (which makes "find all visits with
diagnosis X" painful and limits how many diagnoses a visit can have), or
store lists in one column (which doesn't work well with joins or reporting
tools). Bridge tables avoid all of that and keep the fact table clean.

A few things make my bridges faster than the original junction tables:
- They only contain two integer keys (encounter and code), no descriptions.
- There's exactly one row per visit and code. If the same code was listed
  twice on a visit, the ETL merges it into one row (keeping the lowest
  sequence number for diagnoses, and counting repeats in a quantity column
  for procedures). Because of that, a plain COUNT(*) gives the right answer
  and the slow COUNT(DISTINCT) isn't needed. The diagnosis bridge has
  2,482,009 rows instead of 2,502,126, and the procedure bridge 1,974,342
  instead of 1,999,537.
- Each bridge has a second index the other way round (code first), so
  finding all visits with a certain code is fast.
- In Q2 the descriptions are only looked up for the final 10 rows.

The bridges do help: on my laptop Q2 went from 12.08 s on the OLTP schema
to 3.41 s with the bridges, about 3.5 times faster. Part of that comes from
a shortcut in the query: a pair can never be more common than its rarer
code, so the query first works out the minimum count needed to reach the
top 10 and skips every code that is too rare (only 74 diagnoses and 75
procedures are left). But the bridges can't remove the row explosion
completely. Joining all of them produces about 4.9 million pairs, because
that's simply what the question asks for, so Q2 is still the slowest star
query. That's why I added agg_dx_px_pair: the ETL counts all
the pairs once (1,222,182 of them, with the first and last date each pair
was seen) and stores them with an index sorted by count. Q2 then only reads
the top rows from that index. In pgAdmin that took 0.089 s, and EXPLAIN
ANALYZE showed the database work itself was only 0.79 ms (the rest is
pgAdmin sending and showing the result). The downside is that the summary
is only as up to date as the last ETL run.

The primary diagnosis is also stored directly on the fact table, so the most
common diagnosis questions don't need the bridge at all.

I didn't add a weighting factor to the bridges, because these questions count
visits and don't split money across diagnoses. If someone later wanted
revenue per diagnosis, I would add a weight of 1/diagnosis_count to the
diagnosis bridge.


INDEXES

I designed one index for each business question:

- Q1: ix_fe_date_spec_type on (encounter_date_key, specialty_key,
  encounter_type_key), including patient_key.
- Q2: ix_agg_pair_count on agg_dx_px_pair (encounter_count DESC).
- Q3: ix_fe_index_stays on (specialty_key), including is_readmitted_30d,
  but only for rows where is_index_inpatient_stay is true. Because it's a
  partial index, it only holds about 150,000 of the 1 million rows.
- Q4: ix_fe_claim_spec_amt on (claim_date_key, specialty_key), including
  total_allowed_amount and claim_count.

The INCLUDE part adds extra columns to an index without making them part of
the search key. That way PostgreSQL can sometimes answer a query from the
index alone, without reading the table (this works once autovacuum has run
after the load).

The bridge tables have their primary key on (encounter_key, code_key) and a
second index the other way round. I also indexed patient_key and
provider_key on the fact table for drill-down queries, because PostgreSQL,
unlike MySQL, doesn't create indexes on foreign keys automatically.
